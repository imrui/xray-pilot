# Xray gRPC 隧道控制面、用户无重启热同步与到期撤权架构

- **日期**：2026-06-24（涵盖 `v0.2.1` 地基与 `v0.4.5` / `v0.4.9` / `v0.7.0` 热更新演进）
- **状态**：Implemented（已落地于 `v0.2.1`、`v0.4.5`、`v0.4.9`、`v0.7.0`）
- **关联模块**：`pkg/ssh/grpcdial.go`、`internal/xray/statspb`、`internal/xray/handlerpb`、`internal/xray/handler.go`、`internal/service/livesync.go`、`internal/service/user.go`、`internal/service/revocation.go`

---

## 1. 背景与痛点

在引入热同步之前，每当新增、删除、禁用一名订阅用户，或调整用户所属分组、重置 UUID 时，面板只能将关联节点标记为待同步，随后通过全量 `systemctl restart xray` 生效。这会导致节点上所有正在使用的正常连接瞬间断开。

设计目标是在**不向公网暴露任何管理端口、不引入庞大 `xray-core` 依赖包、不牺牲节点重启后配置持久性**的前提下，实现毫秒级无中断用户权限变更与到期自动下线。

---

## 2. SSH 隧道 + Vendored Proto 轻量客户端底座

### 2.1 本地回环 API + SSH 隧道拨号
- 面板生成的每份节点 `config.json` 固定包含监听 `127.0.0.1:10085` 的 `dokodemo-door` 入站（tag 为 `api-inbound`），路由置顶指向内置 `api`（开启 `HandlerService`、`LoggerService`、`StatsService`）。
- 面板访问远端 gRPC 时，通过 `pkg/ssh/grpcdial.go` 在已认证的 SSH 连接内直接发起本地端口转发（`ssh.Client.Dial("tcp", "127.0.0.1:10085")`），无需在 VPS 防火墙开放 10085 端口，也无需额外维护 mTLS 证书。

### 2.2 独立 Vendored Proto 与注册表约束
- 直接 `go get github.com/xtls/xray-core` 会拖入数百个传递依赖并与面板依赖产生版本冲突。因此仅将所需的最小 `.proto` 定义提取至 `internal/xray/statspb/` 与 `internal/xray/handlerpb/` 独立生成桩代码。
- **两项底层强约束**：
  1. **文件路径全局唯一**：Protobuf Go 运行时按 `.proto` 相对路径注册描述符，`handlerpb` 顶层文件命名为 `handler.proto`，避免与 `statspb` 的 `command.proto` 撞名引发启动 `panic`。
  2. **Proto Package 原样保留**：各协议账号消息的 `package`（如 `xray.proxy.vless`、`xray.proxy.trojan`）直接决定 `TypedMessage.Type` 的 Type URL（如 `xray.proxy.vless.Account`），必须与 `xray-core` 源码逐字一致（仅修改 `option go_package`），否则 Xray 服务端会静默丢弃账号变更。

## 3. `LiveSyncService` 双写一致性与差集对账（v0.4.5）

### 3.1 为什么必须「磁盘 + gRPC 双写」
- Xray 的 `HandlerService.AlterInbound`（`AddUser` / `RemoveUser`）仅修改运行中进程的内存状态，**不会回写磁盘上的 `config.json`**；一旦 VPS 重启或服务重载，仅存在于内存的增删就会全部丢失（更危险的是被删除/禁用的用户会在重启后“复活”）。
- 因此 `applyOnNode` 严格执行**先持久化、后热更新**的双写管线：
  1. 获取节点互斥锁 `lockNode(nodeID)` 与配置租约 `AcquireConfigLease`。
  2. 基于数据库最新有效授权生成完整 `config.json`，经 SSH 预检并原子写入磁盘（`restart = false`）。
  3. 复用同一条 SSH 连接拨号 gRPC，按 `xray.InboundTag(protocol, profileID)`（配置生成与热更新唯一共享的 Tag 来源）逐个托管入站执行账号差异对齐。
  4. **状态守卫**：仅当节点原本无其他非用户级未同步变更（如协议端口或路由模板变更）且全部入站 gRPC 调用成功时，才确认运行态对齐；任一步骤失败立即标记待恢复/漂移，交由受控重启路径兜底。

### 3.2 分组与状态变更的集合差集对账
针对用户编辑（改分组、启停、续期）的复杂组合，统一抽象为节点期望集计算：
- 定义用户在某时刻的有效状态为 `EffectiveActive(now) = Active && (ExpiresAt == nil || ExpiresAt > now)`。
- `desiredNodes = EffectiveActive ? GroupActiveNodes(user) : ∅`。
- 变更前后仅对 `toAdd = desiredNew - desiredOld` 执行增量添加，对 `toRemove = desiredOld - desiredNew` 执行摘除，未发生集合变化的节点零触碰。

### 3.3 漂移检测为何坚持 SSH 读盘而非 gRPC
- Xray 的 `StatsService` 仅为产生过实际流量的活跃用户建立计数器，注册但尚未连接的空闲用户无法从 gRPC 查出，且 Xray 未提供“列举某入站全部已注册账号”的查询接口。
- 因此周期性配置漂移检测保持通过 SSH 安全读取远端 `config.json` 并与面板期望配置比对 SHA256 哈希。

## 4. 过期用户自动下线与撤权闭环（v0.4.9 / v0.7.0）

1. **订阅拦截与运行态摘除分离**：
   - `/sub/:token` 在用户过期后立即返回 `403` 阻止拉取新订阅；但已拿到节点配置的客户端仍能继续连接，必须由后台主动摘除运行态账号。
2. **独立 `ExpiredSweptAt` 标记**：
   - 后台调度器 `expired_user_sweep` 扫描 `Active = true && ExpiresAt <= now && ExpiredSweptAt IS NULL` 的用户。
   - 不直接把 `User.Active` 改为 `false`（避免与管理员手动禁用混淆）；撤权完成后写入 `ExpiredSweptAt`。管理员后续修改 `ExpiresAt` 为未来时间续期时，自动清空 `ExpiredSweptAt` 并触发 `LiveSync` 将用户重新推回各节点。
3. **严格撤权确认（v0.7.0 强化）**：
   - 仅当相关在线节点全部确认移除账号（或因配置异常已安全停止旧权限服务）后，才完成 `ExpiredSweptAt` 标记；离线节点保留待处理状态，待恢复连接后优先对齐，绝不在运行态仍残留旧 UUID 时误报撤权完成。
